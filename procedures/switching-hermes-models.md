## Switching one profile

`scripts/switch-profile-model` sets a profile's main model, base URL and all sixteen helper tasks in one step, after backing up its `config.yaml`. It also updates that profile's `model` and `provider` in the `roster.yaml` of the checkout it runs from (`--roster` picks another file); commit that change, or `scripts/verify-state` reports model drift. Preview both the live and the roster changes with `--dry-run`, which writes nothing. `scripts/verify-state` also fails when a non-retired roster profile is outside the owner model policy (provider `claude-subscription`; `claude-fable-5-2` for the orchestrators, `default` and the advisor; `claude-opus-5-5` for the workers and the reviewers; `glm-5.3` on `zai` for the fifteen GLM workers in service; see "Role models and reasoning effort" below), so an out-of-policy switch stays red until the policy itself is changed.

```sh
scripts/switch-profile-model --profile harness-worker --to glm                       # GLM 5.3 everywhere
scripts/switch-profile-model --profile harness-worker --to gpt --model gpt-6.1-sol   # back to GPT
scripts/switch-profile-model --profile harness-reviewer --to claude-opus             # Opus main, Haiku and Opus helpers
scripts/switch-profile-model --profile default --to claude-fable                     # Fable main; the main /Users/chanbla11mit/.hermes home
scripts/switch-profile-model --profile worker-sol --to gpt --dispatch add            # put a GPT worker back on Kanban
```

- **Targets:**
  - `claude-opus`: `claude-opus-5-5`.
  - `claude-fable`: `claude-fable-5-2`.
  - `gpt`: `openai-codex`, default `gpt-5.6-sol`.
  - `glm`: `zai`, default `glm-5.3`.
- **Helpers under both Claude targets (`claude-opus` and `claude-fable`):** the six light helper tasks (`LIGHT_HELPER_TASKS` in `scripts/verify-state`: `title_generation`, `memory_query_rewrite`, `tts_audio_tags`, `profile_describer`, `skills_hub`, `vision`) go to `claude-haiku-5-5`, and the other ten helper tasks go to `claude-opus-5-5`, all on `claude-subscription` (card `t_e7efc35f`; live record in [`haiku-helper-routing.md`](haiku-helper-routing.md)). Under `claude-fable` this means the helpers do not follow the Fable main model.
- **Helpers under `gpt` and `glm`** follow the main model. Pass `--model` to choose another main model id; under the Claude targets it changes only the main model.
- **Before switching to GPT:** the OpenAI login must be valid again (`hermes -p <profile> auth status openai-codex`). Use a model your plan offers.
- **Before switching to Claude:** the profile needs the plugin in `plugins/model-providers/claude-subscription/`, and `HERMES_CLAUDE_SUBSCRIPTION_CLI` and `HERMES_CLAUDE_SUBSCRIPTION_TOKEN_FILE` in its `.env`.
- **When changes take effect:** new Kanban tasks and new gateway turns pick up the change. Running tasks finish on their current model.
- **Restoring a whole profile instead:** copy its `config.yaml.pre-claude-261017` back over `config.yaml`.

## Switching a project orchestrator between Fable and Opus by hand

The two aliases `opus` (for `claude-opus-5-5`) and `fable` (for `claude-fable-5-2`) are stored in the `model.aliases` key of the `config.yaml` of the five project orchestrators `harness-orchestrator`, `chapt-orchestrator`, `jobcron-orchestrator`, `jss-orchestrator` and `anki-orchestrator` (card `t_617e5b31`, 2026-11-14). The `default` profile and the `advisor` are not covered: they have no `model.aliases` key, and this section does not apply to them. `roster.yaml` and `scripts/verify-state` do not record or check the aliases.

Chat only: type `/model opus` or `/model fable` in the chat of that orchestrator. The choice applies from the next message of that chat. `/new` returns the chat to the model in the `config.yaml` of the profile. Scheduled jobs of the profile are not changed by a chat-only choice.

Whole profile: `/model opus --global` or `/model fable --global`. This writes `model.default` in the `config.yaml` of that profile; no gateway restart is needed. New sessions and scheduled jobs of the profile use the new model. To return: `/model fable --global`.

What `scripts/verify-state` reports while a project orchestrator is on `claude-opus-5-5`: the line `WARN: manual model switch <name>: model.default is <observed model>, roster declares <roster model>` (card `t_822da1dd`). `roster.yaml` keeps `claude-fable-5-2` for the role; a manual switch does not touch it.

The fallback list does not change with a manual switch. When the main model is `claude-opus-5-5` and the subscription request fails, `try_activate_fallback` walks the profile's `fallback_providers` list in order; per `roster.yaml` the list of the five project orchestrators is `anthropic` / `claude-fable-5-2`, then `claude-subscription` / `claude-opus-5-5`, then `anthropic` / `claude-opus-5-5`. Each entry is checked with `should_skip_candidate` (`same_deployment`, scope `MODEL`) against the backend that is active when the entry is reached, not against the original main model. Entry 1 (`anthropic` / `claude-fable-5-2`) is therefore tried first. Entry 2 (`claude-subscription` / `claude-opus-5-5`) is skipped as the same backend only while the active backend is still `claude-subscription` / `claude-opus-5-5`, for example when entry 1 was skipped without being activated; after entry 1 has been activated and its request also fails, the active backend is `anthropic` / `claude-fable-5-2`, entry 2 is not the same backend, and entry 2 is tried.

Where the aliases live and how to add them again: `model.aliases` in the five `config.yaml` files under `/Users/chanbla11mit/.hermes/profiles/`. The two commands, per profile, are `hermes -p <profile> config set model.aliases.opus claude-opus-5-5` and `hermes -p <profile> config set model.aliases.fable claude-fable-5-2`. The backups made before the change are the five files `config.yaml.pre-t_617e5b31` in the same directories as their `config.yaml`.

A permanent change of a role's model stays with `scripts/switch-profile-model` and the roster, as the section "Role models and reasoning effort" above describes.

The statements of this section about `/model`, `/new`, scheduled jobs and the fallback list are read from the Hermes source (`gateway/run_turn.py`, `gateway/slash_commands_session.py`, `cron/scheduler.py`, `agent/chat_completion_helpers.py`, `agent/backend_identity.py`) and have not been run against a live gateway; the statements about `model.aliases` were verified offline against a temporary home and against the five profiles after the change.

## Fallback providers

The script also manages fallback providers. `--apply-fallbacks` writes the `fallback_providers` and `auxiliary_fallback_chain` values that the profile's `roster.yaml` entry declares, and `--clear-fallbacks` sets them to empty lists. Both work with or without `--to` and honor `--dry-run`. `scripts/verify-state` reports any difference as `fallback drift`. The owner-approved Anthropic API fallback for the four Jobcron profiles, including the credential steps and the revert after 2026-11-19, is in [`anthropic-api-fallback.md`](anthropic-api-fallback.md).
