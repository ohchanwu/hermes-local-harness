# Kanban dispatcher reclaims the expired claim of a rate-limited worker and counts it as a failure

Reported: 2026-10-28, by the Anki orchestrator (`anki-orchestrator`, filing session `20261023_184637_9df5ff55`; board `anki`, card `t_e5fe670a`). Recorded from harness card `t_3c579ef1`.

All times are KST (UTC+09:00). Source references are to the installed Hermes Agent (`/Users/chanbla11mit/.hermes/hermes-agent/`, commit `9cf7960f274e`, reported version v0.21.5+6751.g9cf7960), read without running, importing or changing it, and to this repository at commit `b0f9767`.

The 41 `anki-reviewer` runs from 2026-10-27 19:56:30 to 2026-10-28 01:16:03 ended with outcome `rate_limited` and the error text `exited rate-limited (quota wall) — requeued without counting a failure`. The task log shows `Duration: 4m 24s` and `[kanban-worker-exit] rc=75` for this session. The `anki-reviewer` agent log has no further lines, other than plugin registration, until 02:54:46.

- Expected: a worker run that exits with rc=75 is settled promptly as `rate_limited` and is not counted as a failure; a reclaim of a run whose last recorded result is a rate limit is not counted as a failure; and an expired claim is reclaimed close to its expiry time.

## Impact
- A review card whose implementation was complete was blocked after two rate-limited review runs. A person has to unblock it.
- The rate-limit protection of the failure limit does not apply when the settlement goes through the expired-claim path: two rate limits in a row on that path are enough to block a card (the default failure limit is 2).
- Run 58 was started in the same dispatcher pass that reclaimed run 57, without the 5-minute rate-limit cooldown, and met the same rate limit 10 seconds later.

## Diagnosis
Each statement is marked "Established from source" or "Not established".

### (a) How an rc=75 exit is settled as `rate_limited`, and why runs 57 and 58 were not
- Established from source: the worker writes the trailer `[kanban-worker-exit] rc=<code>` to standard error and then calls `sys.exit(code)` (`hermes_cli/quiet_single_query.py:25-40`). The trailer is therefore written before the interpreter shuts down, and it does not prove that the process has exited.
- Established from source: the settlement as `rate_limited` is made only by `detect_crashed_workers` (`hermes_cli/kanban_db_dispatch.py:1296-1313`) through `_reclaim_dead_workers` (`hermes_cli/kanban_db_dispatch.py:1146-1213`). That sweep skips a task whose worker is younger than the crash grace period (30 seconds, `hermes_cli/kanban_db.py:303-305`, `317-319`) or whose worker `_worker_alive` reports as alive (`hermes_cli/kanban_db_dispatch.py:1160-1166`). For a dead worker it takes the exit status from the in-process registry filled by `waitpid` (`hermes_cli/kanban_db_dispatch.py:186-196`, `209-257`, `281-308`) and, when the registry has no entry, from the last trailer in the worker log (`hermes_cli/kanban_db_dispatch.py:260-278`, `1065-1084`). Exit code 75 (`KANBAN_RATE_LIMIT_EXIT_CODE`, `hermes_cli/kanban_db.py:307-309`) is booked as outcome `rate_limited` without a failure count (`hermes_cli/kanban_db_dispatch.py:1097-1106`, `1181-1212`).
- Established from source: in every dispatcher pass, `release_stale_claims` runs before `detect_crashed_workers` (`hermes_cli/kanban_db_dispatch.py:2183-2205`, lines 2195 and 2199; the pass starts with this phase at `hermes_cli/kanban_db_dispatch.py:2348-2352`). When a task's claim has expired and its worker is dead (or its heartbeat is older than one hour), `release_stale_claims` releases the claim, closes the run as `reclaimed` and changes the task status first (`hermes_cli/kanban_db.py:2519-2575`, `2595-2605`). `detect_crashed_workers` then selects only `running` tasks (`hermes_cli/kanban_db_dispatch.py:1150-1154`), so it never sees that task, and the rc=75 trailer is never read. `release_stale_claims` itself reads neither the `waitpid` registry nor the trailer.
- Established from source: the recorded fields `termination_attempted=true`, `terminated=true`, `sigkill=false` do not show that the worker was alive at 02:54:46 or 04:24:20. In `_terminate_reclaimed_worker`, a PID that no longer exists skips the PID-reuse branch, sets `termination_attempted` to true, and the `SIGTERM` then raises `ProcessLookupError`, which sets `terminated` to true (`hermes_cli/kanban_db_dispatch.py:463-489`). The same three values are recorded for a process that exits within 5 seconds of `SIGTERM` (`hermes_cli/kanban_db_dispatch.py:493-495`, `424-430`). A live process that reused the PID would have recorded `pid_recycled` and no termination attempt (`hermes_cli/kanban_db_dispatch.py:477-480`).
- Established from source (derived from the code above and the observed times): if dispatcher passes had run at the default interval of 60 seconds (`hermes_cli/config_defaults.py:1907-1908`, `gateway/kanban_watchers_dispatcher.py:47-55`, `gateway/kanban_watchers.py:52-58`, `285-330`) while the worker process was dead, `detect_crashed_workers` would have settled run 57 as `rate_limited` within about one minute of 01:25:43, before the claim expired at 01:36:19. If the worker process had stayed alive and the passes had run every 60 seconds, `release_stale_claims` would have extended the claim by 15 minutes at each expiry (`hermes_cli/kanban_db.py:279`, `2533-2536`, `2608-2635`) until the first pass after the heartbeat was older than one hour (`hermes_cli/kanban_db.py:288`, `2531`), that is between about 60 and 76 minutes after the last heartbeat (about 02:21 to 02:37 for run 57, about 03:55 to 04:11 for run 58). The observed reclaims came 93 minutes (run 57) and 89 minutes (run 58) after the last heartbeat. Neither case matches the observed times while passes run every 60 seconds, so dispatcher passes that evaluated board `anki` did not run at the default interval during these two windows.
- Not established: why no dispatcher pass settled either run between the session end and the reclaim. The source shows these conditions under which passes do not evaluate a board, but no evidence on this card selects one of them: the host was asleep; the dispatcher was paused (`gateway/kanban_watchers.py:297-300`); another process held the board's dispatch lock, so passes were skipped (`hermes_cli/kanban_db_dispatch.py:1966-2003`); passes for the board raised an exception or the board was quarantined (`gateway/kanban_watchers_dispatcher.py:176-210`); one pass on any board blocked the loop, because the loop waits for each pass (`gateway/kanban_watchers.py:308`); or `kanban.dispatch_interval_seconds` was configured above the default. The profile configuration and the gateway log were not read on this card.
- Not established: whether pid 13106 or pid 13904 was still alive after its trailer was written. The board events (for example `claim_extended` events with `reason` `pid_alive` between the claim expiry and the reclaim, `hermes_cli/kanban_db.py:2624-2635`) and the gateway log were not available on this card.
- Established from source: the claim lock value has the form `<host>:<pid of the claiming process>` (`hermes_cli/kanban_db.py:1164-1171`). Runs 57 and 58 and this harness card's own run 188 (claimed on 2026-10-28) carry the same value `Chanwus-MacBook-Pro-2.local:60872`, which indicates that one dispatcher process made all three claims. Not established: whether that process was the one that recorded the two reclaims.

### (b) Which reclaim outcomes count toward `effective_limit`
- Established from source: `_record_task_failure` increases `consecutive_failures` by one and blocks the task with a `gave_up` event when the count reaches `effective_limit`, which is the task's `max_retries` if set and otherwise the dispatcher's `failure_limit` (default `DEFAULT_FAILURE_LIMIT = 2`, `hermes_cli/kanban_db_dispatch.py:34-36`; configuration default `hermes_cli/config_defaults.py:1909-1911`; logic in `hermes_cli/kanban_db_dispatch.py:1345-1465`, lines 1376-1377, 1391, 1394-1400 and 1429-1464). The counter is reset only by a completed task, by reassignment, and by the operator command `reclaim_task` (`hermes_cli/kanban_db_dispatch.py:1510-1522`, `hermes_cli/kanban_db.py:1642`, `2638-2642`).
- Established from source: these paths count a failure: every expired-claim reclaim that releases a claim, outcome `reclaimed` (`hermes_cli/kanban_db.py:2576-2584`; its docstring states this intent at `2492-2496`); a run that exceeded `max_runtime_seconds`, outcome `timed_out` (`hermes_cli/kanban_db_dispatch.py:728-739`); and a dead worker classified as a crash, a nonzero exit other than 75, or a signal (`hermes_cli/kanban_db_dispatch.py:1276-1290`). A protocol violation (rc=0 while running) uses its own count of consecutive violations (`hermes_cli/kanban_db_dispatch.py:1232-1261`, `929-957`), and a terminal provider error (rc=78) blocks at once (`hermes_cli/kanban_db_dispatch.py:1262-1275`).
- Established from source: these paths do not count a failure: a dead worker with exit code 75 (`hermes_cli/kanban_db_dispatch.py:1198-1212`); a run without heartbeat progress reclaimed by `detect_stale_running` (`hermes_cli/kanban_db_dispatch.py:748-842`, stated at `760-762`); and a running task with broken claim bookkeeping requeued by `reconcile_orphaned_running` (`hermes_cli/kanban_db_dispatch.py:845-908`).
- Established from source: a reclaim of a run whose process had exited with rc=75 counts as a failure when it goes through `release_stale_claims`, because that path calls `_record_task_failure` without consulting the run's exit code (`hermes_cli/kanban_db.py:2526-2584`). This matches the `gave_up` payload (`failures` 2, `effective_limit` 2, `limit_source` `dispatcher`, `trigger_outcome` `reclaimed`): the 41 earlier rate-limited runs left the count at 0 (`hermes_cli/kanban_db_dispatch.py:1198-1207`), and the reclaims of runs 57 and 58 raised it to 1 and 2.
- Established from source: after such a reclaim the latest run has outcome `reclaimed`, and `last_failure_error` holds `stale_lock=...` (`hermes_cli/kanban_db_dispatch.py:1411-1415`, `1433-1435`). The rate-limit cooldown of 300 seconds applies only when the latest run has outcome `rate_limited` (`hermes_cli/kanban_db_dispatch.py:78-80`, `1560-1583`), so run 58 could be started in the same pass as the reclaim of run 57.

### (c) When expired claims are checked, and why the reclaim came 78 minutes after expiry
- Established from source: `release_stale_claims` runs at the start of every dispatcher pass for each board (`hermes_cli/kanban_db_dispatch.py:2195`, `2348-2352`; `gateway/kanban_watchers_dispatcher.py:176-200`), at the default interval of 60 seconds (`hermes_cli/config_defaults.py:1907-1908`). It selects running tasks with `claim_expires` earlier than the current time (`hermes_cli/kanban_db.py:2519-2525`). For a host-local worker that `_worker_alive` reports alive, and whose heartbeat is not older than 3600 seconds, it extends the claim by the claim time limit of 900 seconds instead of reclaiming it (`hermes_cli/kanban_db.py:279`, `288`, `2531-2536`, `2608-2635`). Otherwise it signals the worker, holds the claim for 120 seconds if the worker survives (`hermes_cli/kanban_db.py:292`, `2538-2547`), and releases it.
- Not established: why the reclaim came 78 minutes after the claim expired. As stated under (a), the observed delay does not match the code with passes every 60 seconds, whether or not the worker process was alive; the cause is one of the conditions listed under (a), and no evidence on this card selects one.

### Item 2: repository-owned code that could keep a worker process alive after the session ends
- Established from source: the claude-subscription plugin (`plugins/model-providers/claude-subscription/`) starts no thread of its own and registers no exit handler. Its Claude CLI child is started in a new session (`runtime.py:23-24`) and is stopped with `SIGTERM`, then `SIGKILL`, on cancellation (`runtime.py:113-141`). The rate-limit rejection is raised at `client.py:602-604`, and the exception path calls `cancel()` (`client.py:612-614`), which shuts down the bridge socket and closes the child processes (`client.py:787-796`; `bridge.py:129-136`). A child process in its own session does not keep the parent Python process from exiting.
- Established from source: when `create()` is called while an event loop is running, the plugin runs the request with `asyncio.to_thread` (`client.py:209-217`). That uses the event loop's default thread pool, and the standard library in the installed Hermes runtime joins those threads before the interpreter exits (`.hermes-runtime/python/generation-1789815844-16479-53247542/cpython-3.13.15-macos-aarch64-none/lib/python3.13/concurrent/futures/thread.py:23-37`, under the Hermes Agent install directory). A request on that path that is still in progress when the worker calls `sys.exit` would delay the process exit until the request ends. Each request waits at most its own response time limit for the client lock (`client.py:227-228`).
- Not established: whether any such request was in progress when runs 57 and 58 ended. Even if one was, a live process alone does not explain the observed reclaim times (see (a)). No change to this code is proposed on this card; if a later card confirms a live worker process after the trailer, harness-orchestrator can file a separate card for it.

## Likely area
Hermes Agent Kanban dispatcher: the order of the reclaim phase (`_run_reclaim_phase`, `hermes_cli/kanban_db_dispatch.py:2183-2205`), the failure count in `release_stale_claims` (`hermes_cli/kanban_db.py:2487-2592`), and the scheduling of dispatcher passes in the gateway (`gateway/kanban_watchers.py:257-332`).

## Requested
Changes requested from Hermes Agent:
1. Before `release_stale_claims` reclaims a claim whose worker is dead, settle the run from its exit status (the `waitpid` registry or the `[kanban-worker-exit]` trailer), as `detect_crashed_workers` does; or run `detect_crashed_workers` before `release_stale_claims` in each pass. An exit with code 75 must then be booked as `rate_limited`, without a failure count, and with the rate-limit cooldown.
2. When `release_stale_claims` reclaims a run whose worker log ends with `[kanban-worker-exit] rc=75`, do not count a failure toward `effective_limit`.
3. Record in the `reclaimed` event whether the worker PID existed before the termination attempt, so that `terminated=true` can be told apart for a process that had already exited and a process that the dispatcher stopped.
4. Log a warning when the time since the previous dispatcher pass for a board is much larger than `dispatch_interval_seconds`, so that a delay such as the 78 minutes reported here can be attributed (host sleep, pause, a blocked pass, or a held dispatch lock).
