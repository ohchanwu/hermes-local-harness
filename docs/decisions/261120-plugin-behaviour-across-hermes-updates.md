## Decision

1. Each plugin uses Hermes only through documented interfaces when Hermes documents one for the purpose. The plugin guide promises that these keep working after a normal upgrade (plugin guide lines 240 to 241).
2. When no documented interface exists, the plugin keeps the dependency, checks for it, and when the expected Hermes object, field or signature is absent, it turns off only the one feature that needs it and writes one Python `logging` record at level WARNING per process that names the missing Hermes name. It never raises into Hermes and never refuses all requests because of a Hermes change.
3. One test per plugin runs against the installed Hermes after every update and fails when a dependency is missing (section 3).
4. Seven implementation changes, numbered in section 4. The controller files one card per change.

Where the dependency is a result field or an event payload field, Hermes produces the value only at run time, so the check runs at the first use and not at plugin load. The card asks for a check at plugin load; this record uses a check at the first use for these cases because the value does not exist at load time.
