# Native triage and review-origin routing

- Fence a fixture-boundary incident to its affected commands and state. Preserve evidence and separately gate unauthorized incident inspection/remediation, but continue independently authorized isolated implementation unless an evidenced dependency makes it unsafe. Do not turn cleanup permission or a routine failed test into a campaign-wide human prerequisite; require per-subprocess removal of optional integration activation and inspected, targeted disposable-fixture commands.
- Treat `specify_triage_task` as specification/resumption, not an implementation-ready guarantee. Native recomputation can restore `review` from prior lifecycle events even after changing the assignee. Read back status before reporting or admitting a dispatch receipt.
- Do not use `promote` on `review` or `triage`: the installed CLI accepts only `todo` and `blocked`. For an authorized same-card implementation continuation already in `review`, use the native `reopen_review_task` operation, then immediately reassign the exact independently approved project worker. Reopen restores the historical implementer; verify the final destination and preserve counters/events rather than editing SQL or forcing a gateway dispatch.
- Reclaim a wrong-phase claimed actor, verify its termination and exact tracked-source/effect boundary, and reconcile actual run IDs under the existing infrastructure budget. Keep controller routing fault attribution distinct from worker semantic defects. Avoid leaving a dispatchable wrong phase while waiting for process reap; sequence the correction using supported native operations and verify no overlapping worktree actor before accepting the new receipt.
- Verify implementation-ready receipts using the installed native lifecycle semantics. Ready claims may omit `source_status`; review claims explicitly carry `source_status: review`. Confirm `_retry_status_for_run` and the preceding transition instead of rejecting a healthy claim for an absent optional field. Correct the observer without restarting healthy work.
- Treat a native `crashed` or `blocked` outcome as logical lifecycle evidence, not proof that its process exited. A controller block can race a new claim and close a genuinely spawned worker row; do not call that row controller-only merely because its reason was controller-authored. Inspect spawn/PID evidence and both exact actors before changing inputs. Fence and reap only a verified stale actor after task/profile/cwd/process-group identity checks; preserve a delayed or failed termination observation rather than claiming immediate absence. Do not restart the healthy current owner or reinterpret a crash as semantic approval.
- Preserve a crashed review's report and independently verified successor verdict with their actual run authorship. Use per-run output namespaces to avoid overwriting evidence. If a shared report was overwritten, recover the original only from retained exact output and verify its originally recorded hash; never reconstruct missing text by inference. Correct reviewed inputs only after the current review is terminal and all reviewing actors are absent, then pin new bytes for same-card re-review.
- Ground a migration-recovery document correction in the entire startup mechanism, including embedded filename/digest maps and tree-identity pins, not SQL files alone. Specify the minimal manifest-metadata allowance without weakening old pins or validation algorithms, and retain actual recovery/forward-return rehearsal. Additive SQL does not prove an unchanged old binary can open its ledger.
- Parse large native JSON inside the subprocess and return only necessary fields. A terminal presentation layer can truncate or redact a full card export into invalid JSON; that output is not authoritative evidence of malformed board data.
- Record pending attempts with actual claimed run IDs, not forecast IDs. Append successor snapshots for every infrastructure retry/completion; preserve all historical semantic rejections and material-difference reviews. Explicit migration reconstructions are present records, not backdated execution evidence.
- Apply project retry limits independently of native scheduler counters: a native rate_limited exit may say it requeues without counting a failure, but quota failures still consume bounded-convergence infrastructure allowance. Fence the exact card when that allowance is exhausted; do not keep free-retrying, invent a different strategy from a profile change, or treat unrelated authorized work as stopped.
- Distinguish controller-created lifecycle rows from executed workers even when native rows inherit the card's assignee profile. A controller block can create a run with worker_pid=null and no spawn event. Preserve that coordination row but do not count it as implementation, semantic review, or another attempt; bind executed authorship to actual claims/spawns and observed actor identity.
- Fence prospective strategy review separately from implementation acceptance on the same card. Freeze the rejected source, bind the exact written strategy/hash and limited read-only scope, and require an independently eligible material-difference verdict before appending a new approach. Prefer a native terminal transient coordination block after the bound prospective verdict when activation belongs to the controller; ordinary request-changes can automatically start forbidden implementation, while complete would falsely accept the rejected code. Actual human decisions use needs_input. Never complete the original implementation card from strategy readiness or relabel a controller-created native handoff row as executed implementation.
- Do not prescribe native request-changes for a controller-only prospective handoff whose profile is null: it requires valid implementer provenance and refuses that return. Preserve the controller handoff and actual independent prospective verdict as distinct records; never fabricate an implementer to satisfy routing. After an eligible verdict, the controller may explicitly activate the exact reviewed approach, append its budget entry, replace the read-only phase with the binding implementation contract, and assign/promote the same inactive blocked card through supported lifecycle operations. Verify the new actual worker claim/cwd; prospective eligibility is never code acceptance or a budget reset.
- Reconcile automatic implementation requeues after a controller-owned prospective verdict. A worker's read-only stop awaiting controller activation is coordination evidence, not another candidate or infrastructure retry; preserve it without resetting budgets. If activation handback recurrence routes an inactive card to triage, retain the original task/source/authority and independently bound eligibility. Append the eligible new approach and write its binding implementation phase while still nondispatchable, then use the inspected native dashboard PATCH update_task with explicit board and matching assignee+ready to recover it. Read back actual phase/status/assignee and verify the new claimed actor/cwd. Do not invoke specification/decomposition merely to exit recurrence, rewrite SQL, reset failed history or dispatch code before eligibility. Genuine underspecified triage still requires normal specification before implementation.
